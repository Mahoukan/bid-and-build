# Bid & Build

A multiplayer auction party game for 2–5 players, including the host. Create a design or host a published template, bid with fictional whole-number currency and compare everyone's purchases and balances. Guests need no account. Administrators manage permanent templates. Rooms, content images, accounts and purchase ledgers persist in SQLite.

Descriptions appear directly on cards, preserving line breaks. Player screens keep bidding controls separate from the scrollable current description; collections share a vertical scroll area. The read-only shared display uses page flow for long descriptions and takes no seat. Appearance presets, light/dark mode, accents and personal backgrounds stay in each browser.

## Run locally

Use **Node 24 LTS** and **npm 11.19.1–11.x**. In Windows PowerShell, use `npm.cmd` instead of `npm`.

```sh
npm ci
npm run setup
npm run dev
```

Open **http://localhost:5173**. Vite proxies API and Socket.IO traffic to port 3000. `/health` reports readiness. Setup creates a missing root `.env` with a random secret and never overwrites an existing file. Stop with Ctrl+C.

For a production-style local preview, run `npm run build`, set `APP_ORIGIN=http://localhost:3000` in your private environment, then run `npm start`. Open **http://localhost:3000**. Restore the development origin before running Vite again. Remote production administrator sessions require HTTPS.

For phones on a private LAN, set `APP_ORIGIN` to the PC's LAN origin, such as `http://192.168.1.25:5173`, restart development and open that same URL on every device. Allow port 5173 through the private-network firewall if needed. Each browser/origin has separate drafts and appearance; export/import designs to move them.

## Configuration and commands

Runtime environment variables override root `.env`. Keep secrets out of `VITE_*` variables, build arguments, URLs and Git.

| Variable | Local default | Production |
| --- | --- | --- |
| `NODE_ENV` | `development` | `production` (`start` selects this) |
| `HOST` | `0.0.0.0` | `0.0.0.0` |
| `PORT` | `3000` | `3000` inside Docker |
| `DATA_DIR` | `./data` | `/data` |
| `APP_ORIGIN` | `http://localhost:5173` | `https://bid.arulmozhis.com` |
| `SESSION_SECRET` | Generated by setup | Private stable runtime secret, 64–1024 characters |
| `TRUST_PROXY` | Empty | Actual reverse-proxy IPs/CIDRs, comma-separated |

Origins must match exactly, without a path or trailing slash. Empty `TRUST_PROXY` ignores forwarded addresses; clients behind a proxy share its rate limits. Never use unrestricted proxy trust, a hop count or an all-addresses network. Preserve the production secret across releases: it protects private retry receipts, display capabilities and administrator CSRF values.

| Command | Purpose |
| --- | --- |
| `npm run setup` | Create missing local configuration |
| `npm run dev` | Watch server and React client |
| `npm run check` | ESLint and TypeScript checks |
| `npm run build` | Compile server and build client |
| `npm start` | Serve the built application |
| `npm run admin:create` | Create an administrator through private prompts |
| `npm run admin:reset-password` | Reset one administrator and revoke their sessions |
| `npm run db:migrate` | Apply built database migrations |
| `npm run db:backup -- NEW_DIR` | Create a consistent database/image backup |
| `npm run db:restore -- BACKUP_DIR NEW_DATA_DIR` | Validate and restore into new storage |

Build before running administrator or database commands. Startup also applies migrations transactionally before listening. Keep the single root lockfile and install native dependencies on the target OS; never copy Windows `node_modules` into Docker or omit optional dependencies.

SQLite (`better-sqlite3`) and Sharp use native prebuilt packages. The npm `allowScripts` policy disables an unnecessary SQLite rebuild and permits esbuild's install script. A SQLite source-build fallback needs Python 3 and a C++ toolchain (Visual Studio Desktop development with C++ on Windows; make/g++ on Debian), plus a deliberate install-policy change. Sharp's source build additionally needs its supported node-addon-api and libvips toolchain.

Dependency maintenance: `npm audit --omit=dev` currently reports a high-severity denial-of-service advisory in the locked transitive `body-parser` 2.3.0 ([GHSA-27r3-jxmh-p828](https://github.com/advisories/GHSA-27r3-jxmh-p828)). Address it before the next production release.

## Playing and editing

At `/builder`, select the dragon starter, create a design or import JSON, then save explicitly. Drafts live in IndexedDB; clearing site data can erase them. Export important drafts before changing browsers or origins. Hosting uploads a temporary game snapshot and its content images. Personal appearance and backgrounds are never uploaded or exported.

The portable format is `bid-and-build-template`, version 1; [the dragon starter](samples/dragon-game.json) is an editable example. Templates contain 1–200 ordered options, titles up to 120 characters and descriptions up to 4,000 characters. Currency settings are positive whole numbers up to 1,000,000. Selected images must be PNG/JPEG, at most 5 MiB, 20 megapixels and 8,192 pixels per side. Processing fits images within 1,600 pixels per side and 1 MiB each. Portable images use base64 bytes, never remote URLs or paths. Total images are limited to 8 MiB and JSON imports to 12 MiB. Imports validate and re-encode images before replacing the editor.

Hosting creates the host's player seat. Share the room link and start with 2–5 connected players; joining closes once play begins. Defaults are budget $20, opening price $1 and minimum increase $1. Bids may jump above the minimum. Only the buyer pays, once; a leader cannot raise or withdraw their own bid. Give Up affects the current option only. Concessions are sequential: a sole remaining eligible player automatically buys at the opening price when no bid exists. With a leader, inability of all remaining opponents to afford the next raise settles the existing bid. No eligible players means unclaimed. Skip requires no bid; Bet All requires exact-amount confirmation. Confirmed End settles an existing bid even while paused and leaves an incomplete result. Results compare builds without assigning a scored winner.

Refresh restores a saved seat. Keep a private copy from **Game menu → Private recovery code** to transfer the same seat to another browser/device. Recovery preserves money, purchases and the original host permission, replacing the previous controller. A public room code cannot recover a seat. Another tab needs explicit takeover. Replace Code invalidates the previous recovery code; game recovery never signs in an administrator.

Player disconnects pause bidding and reveals. Reconnecting does not resume: the host explicitly chooses Resume, including when proceeding with someone absent. Temporary absence preserves eligibility and binding bids. **Sit Out** is a confirmed host action for an offline, permanently departed non-host player while paused. It preserves purchases and binding bids but excludes new participation for that run; Play Again resets it. Shared-display disconnects have no effect. Interrupted games restore paused after a server restart. Rooms expire after 24 hours without player activity; a display alone does not extend expiry.

## Administrator setup

There is no default account or public signup. Build, then run `npm run admin:create` in a private interactive terminal. Enter a username and a 15–128 character password twice at the hidden prompts. Never pass credentials through command arguments or environment variables. Sign in at `/admin` to create, edit, publish, unpublish or delete templates. Guests browse at `/templates`; future options stay hidden until revealed in play. Existing rooms retain their own content and images when a source template changes or is deleted.

`npm run admin:reset-password` privately prompts for the account, new password and confirmation, then revokes that account's sessions. In Docker, use `docker exec -it YOUR_CONTAINER npm run admin:create` or `docker exec -it YOUR_CONTAINER npm run admin:reset-password`. These commands use configured persistent storage and can run while games are active. Production administrator cookies require HTTPS and the exact configured origin.

## Docker and Coolify

Build with `docker build -t bid-and-build:local .`. The Dockerfile uses Debian Bookworm, Node 24.22.1 and npm 11.19.1, includes compiled maintenance commands and runs as `node` (UID/GID **1000:1000**). CI performs a clean install, lint/type checks, application build and Docker image build.

| Setting | Value |
| --- | --- |
| Build method / context | Root `Dockerfile` / repository root |
| Listen address / container port | **0.0.0.0:3000** |
| Coolify host mapping | **3108 → 3000** |
| Public origin | **https://bid.arulmozhis.com** |
| Persistent mount / `DATA_DIR` | **/data** |
| Replicas | **1** |
| Readiness route | **/health**, internal port 3000 |
| Stop grace period | **30 seconds** |

Keep `SESSION_SECRET` private and reuse the existing persistent mount. `/data/bid-and-build.sqlite` and WAL/SHM sidecars hold templates, images, accounts, rooms and ledger data. Bind mounts must be writable by 1000:1000. Images are database BLOBs; there is no public upload directory.

Use Coolify's **Consistent name (no rolling updates)** setting and verify the old process stops before its replacement starts. Never overlap replicas against the database. Shutdown stops admission, drains accepted work and closes SQLite; the emergency deadline is 25 seconds. The Docker health check calls `/health`, which becomes ready only after migrations and a live database query. Check HTTPS, administrator login, joining/bidding/reconnecting and paused-game recovery after deployment. Do not clear storage to fix startup errors.

## Backup and restore

Create the parent `backups` directory, then choose new destination names:

```sh
npm run db:backup -- ./backups/before-update
npm run db:restore -- ./backups/before-update ./backups/restored-data
```

Both destination directories must not already exist; parents must exist. Backup may run while the app is active. It uses SQLite's online backup API and writes `bid-and-build.sqlite` plus `manifest.json`, with schema, integrity, foreign-key and checksum checks. All server content images are included. Browser drafts and personal backgrounds are separate; export drafts from the builder.

Keep the complete backup private and copy it off-server. Retain the matching application version, environment and `SESSION_SECRET` separately. Never copy a live database file alone or discard its WAL. For an offline archive, stop every writer and archive the entire data directory. The restore command accepts manifest-based backups from `db:backup`, not arbitrary archives.

In Docker, use `docker exec YOUR_CONTAINER npm run db:backup -- /data/backup-before-update`, then `docker cp YOUR_CONTAINER:/data/backup-before-update ./backups/before-update`. Restore into a new directory or volume. Stop the old app and maintenance writers before selecting restored storage, then start exactly one instance with the matching secret. Check templates/images, purchases, balances and paused-seat recovery before resuming. Normal room/session expiry still applies.

Back up before schema changes. Never edit an applied migration. Backup/restore requires the application's matching schema history; reverting an image does not undo migrations. Roll back with the matching older application and its pre-update backup in separate storage, preserving the original data until verified.
